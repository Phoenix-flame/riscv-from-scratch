Chasing 50 MHz

The Linux board core went from 18.2 MHz to 59.7 MHz after routing, and the board now runs it at 55.56 MHz. Step 58 reached 50 MHz one critical path at a time. Steps 59 to 62 put the caches and a branch predictor in block RAM, took a cycle off most loads and stores, and cleared four more paths. This report shows each fix and how much margin is left.

FCLK1, the core's clock 11.11 → 55.56 MHz IO PLL ÷ 18, UART divisor 30; the Linux shell in 5.4 s instead of 26 s

Timing margin 7.4 % worst path 16.8 ns against 18 ns; the 50 MHz build (16.7 %) is the fallback

The short version. Step 58 moved long chains off the critical path, then kept the best placement seed: 51.47 MHz, and the board ran at 50. Step 59 put the caches in block RAM, and the smaller design routed at 55–58 MHz on every seed. Steps 60 and 61 spent that headroom on work per clock: a block-RAM branch predictor, and one EX cycle for a load or store in the last one's page. CoreMark per MHz went from 1.77 to 2.53. Step 62 then moved the board to 55.56 MHz, after four more path fixes that change no cycle count.

The caveat. 7.4 % margin, on an estimate from prjxray's timing data, is not a sign-off. A core that is too slow misbehaves at random rather than failing cleanly. If the board does that, OpenZynq commit 6a6a314 has the 50 MHz Step 59 build, with 16.7 % margin, and 422f1e3 the 33.33 MHz one. Nothing here has run on a board yet.

Where the clock went

nextpnr reports one critical path per clock: the single slowest register-to-register path. A timing fix here means reading that path, finding the stage that makes it long, and registering it or moving it off the path. Then rebuild (about 5 minutes) and read the next one.

Why the gains level off

The first paths were long because they held too much logic: two DSP48 multipliers and an adder in series, then a result mux, the address, the TLB and the fault logic. The later paths hold 2–3 ns of logic and 17–22 ns of wire. nextpnr spreads the core across the die, and each hop between LUTs costs 1–3 ns. Once that's true, removing a LUT level from one path just hands the title to the next path.

Round 1: the execute stage and the flushes

Every fix is a parameter on cpu_pipe_u that defaults to 0. Only the board build (fpga_top_linux), its simulation and the *_board test cores turn them on, so every other configuration of the core stays cycle-identical.

The load/store path: an address adder, a registered multiplier, a registered TLB lookup

  • AGU: a load's or store's address comes from its own adder (rs1 + imm), not the ALU.
  • MUL_2C: the multiplier latches its operands and holds EX for 3 cycles. One signed 33×33 multiply covers all four RV32M multiplies (12 → 4 DSP48s).
  • XLATE_2C: a load or store spends two cycles in EX. It looks up the D-TLB and registers the answer (xl_*), then makes the fault, region and commit decisions from those registers.

VALID_FLUSH: a flush clears two bits, not two hundred

A mispredicted branch used to reset every field of IF/ID and ID/EX: operands, immediate, PC, instruction, control bits. That put the branch compare on the reset pin of a few hundred flip-flops spread across the die.

With VALID_FLUSH a flush clears only valid, and in EX/MEM the control bits. The other fields load as usual and hold a dead instruction's values. Nothing downstream acts on an invalid instruction: forwarding checks reg_write, the D-port checks mem_read/mem_write, and retirement checks valid. In round 2, IF/ID's data fields also lost the flush from their enables.

REG_REDIRECT: the branch redirects one cycle later

With no branch predictor, every taken branch or jump is a misprediction. It used to steer the PC mux in the same cycle it resolved in EX. With REG_REDIRECT the redirect goes into a register (rr_valid, rr_pc) and takes effect a cycle later. The wrong-path instruction that entered EX meanwhile is killed through one gate, idex_valid = idex_valid_q & ~rr_valid, because everything EX does is gated by idex_valid. In round 2 the misaligned-target exception also came off the compare. Bit 1 of a target is a 2-bit add. A branch can be misaligned only through its immediate, which compiled code without C never has, so such a branch spends one more cycle in EX and traps on the registered outcome.

Round 2: forwarding, fetch, and the decodes

FWD_PRE: the forwarding compares a cycle early

After round 1 the worst path started at a forwarding compare: is EX/MEM's or MEM/WB's rd the register EX is about to read? That compare sat in EX, in front of the operand muxes and the ALU. The register numbers are all known a cycle earlier, so FWD_PRE computes the four matches from the values the registers will hold next cycle and stores them. In EX the select is then one registered bit ANDed with reg_write. This was the biggest single gain of round 2: 40.8 → 49.4 MHz.

The rest of round 2

  • IF_PAGE: a registered translation for the fetch page. Every fetch ran pc → the I-TLB's CAM → the address → the region check and I-cache tags → if_ok → the PC's enable. Now the I-TLB's answer for the current page is kept in registers, and a fetch in that page uses {ip_ppn, pc[11:0]}. A new page costs one lookup cycle. Anything that could change the answer drops the copy: any CSR write, a trap, mret/sret, sfence.vma, or the end of any walk. A simulation-only check compares the copy with the live lookup whenever it is used, through the Sv32 programs and the full Linux boot. Cost: 0.4 % on the Linux boot.
  • Carry-free region checks, in every configuration. pma() computed a − base < size, two chained carry chains on every fetch and access. Power-of-two regions on their alignment now use a masked compare, and the ROM (0x1000–0x5000) uses two parallel compares on its aligned bits. 0 mismatches against the old formula in 4.8M checks. The walker's PTE address {ppn, 0} + 4·vpn can never carry, so it's now a concatenation.
  • The misaligned-target exception off the branch compare (above). It's covered by a new directed test, rv32mx-ma_tgt, with two mutants caught.
  • HPM_LATE: hardware performance counters 3–7 (implementation-defined events) count a cycle late, so the D-port stall no longer drives 320 counter enables. mcycle and minstret stay exact.
  • A killed fetch-side walk's fault, like its fill, is suppressed through the registered killed flag.

Step 58's last 2 %: placement seeds

By the end of round 2, rebuilding the same RTL with a different nextpnr seed moved the result more than any further change did. The seed is a plain input: the same netlist and seed give the same placement, so the build can keep the best one. The boot ROM's contents are part of the netlist, so the sweep ran on the real 50 MHz build.

Round 3: block RAM (Step 59)

A profile of the Linux boot after Step 58 showed where the cycles went: a quarter retired instructions, and half waited on the 2 KiB caches. Step 59 put both caches in block RAM, at 16 KiB each. Block RAM answers in the cycle after it gets its address, so the core now tells each cache, a cycle early, where it will read next.

The timing gain came from somewhere else. The first block-RAM caches kept their valid and dirty bits in 1,536 flip-flops, each with its own set and clear decode, and routed slower than Step 58. Moving those bits into the tag RAM took out about 4,500 cells, a third of the design. With the core that much smaller, every one of nine seeds routed at 55–58 MHz, and 50 MHz had 16.7 % margin. Linux reached its shell at cycle 304.4M instead of 374.8M.

Round 4: more work per clock (Steps 60 and 61)

With headroom on the clock, two kinds of cycles stood out. Every taken branch flushed, because the board had no predictor. And every load and store spent a second cycle in EX for XLATE_2C's registered lookup.

  • A branch predictor in one block RAM (BPRED=2). It has 512 entries of {tag, counter, target}, read at the PC's next value the same way as the caches. There's no valid bit and no reset clear, because EX checks every guess. The counter rides down the pipe with the instruction instead of being read again. The target check compares against values ID works out (pc + imm; for jalr, rs1 == predicted − imm), so no adder sits in front of the compare.
  • One EX cycle in the last page (D_PAGE). A load or store whose base register needs no forwarding has its exact address in ID: the register value plus the immediate. If that address is in the page of the last access, the instruction carries that page's registered translation into EX and skips the lookup cycle. A CSR write, a trap, mret/sret or sfence.vma drops the copy, and a simulation-only check compares it with the live D-TLB.

Dhrystone moved further than CoreMark: 0.276 DMIPS/MHz at Step 58, 0.747 with the bigger caches, and 1.173 now. In the Linux boot, flush cycles fell from 52M to 3M.

Round 5: 55.56 MHz (Step 62)

The next FCLK1 step that keeps 115200 baud within 0.5 % is IO PLL ÷ 18, with UART divisor 30. The first sweep timed at 55.56 MHz passed on 4 of 10 seeds. Three more rounds of fixes, none of which changes a cycle count, brought that to 9 of 10.

  • System commits without the hold. A CSR access, mret, sret or sfence.vma never holds EX, so their commits now wait only for freeze, not for ex_hold and the page walker's state behind it. A simulation-only check stops any run in which one does hold EX.
  • The SC's reservation match, registered. freeze depended on a 32-bit compare of the reservation against MEM's address. The compare is now made as the SC enters MEM, and checked against the old one in simulation.
  • A coarser ROM decode. The core's region check lets nothing outside a real region reach the D-port, so "below 1 MiB" now stands in for the ROM's exact range.
  • The D-cache's word select from a register, and the walker's PTE every cycle. The 8-to-1 word mux over a line from 4 block RAMs no longer waits for the walker-or-MEM address mux, and the walker's level-1 PTE register no longer waits for that PTE's decode.

The shipped seed's worst path is the core's own EX loop: forwarding → ALU → the EX result, 16.8 ns against an 18 ns budget.

The clock

FCLK1 is the PS's IO PLL (1000 MHz) divided by two 6-bit dividers. Only some steps give 115200 baud within 0.5 %; those up to 55.56 MHz all give 115,741 baud. Step 58 took 50 MHz (÷ 20, UART divisor 27). Step 62 took the next step, 55.56 MHz (÷ 18, divisor 30). The one after, 62.5 MHz (÷ 16, divisor 34, 114,890 baud), is past every seed.

The PS program writes FPGA1_CLK_CTRL = 0x00600300 (divisors 3 × 6) right after ps7_init. The board ROM and device tree are built with PLAT_CLOCK_HZ=55555556 UART_DIVISOR=30, and nextpnr gets --freq 55.56 --seed 7. The U-Boot + Linux image reads the clock from the device tree the ROM writes, so it is the same image as at 50 MHz.

What's left

The shipped seed's worst path is now forwarding → ALU → EX result: the loop any five-stage core has, with 1.7 ns of logic and 15.1 ns of wire. There is no long chain left to move.

More clock

The next baud step, 62.5 MHz, is past every seed. Reaching it would take a placement that keeps the core compact, either a floorplan or Vivado's placer and router, which usually do much better on 7-series than nextpnr-xilinx 0.9.3.

More per clock

A load whose base comes from the instruction just ahead still takes two EX cycles, and a return-address stack would catch most of the remaining mispredictions in call-heavy code. The Linux boot is now mostly memory: of 331M cycles, 64M wait on fetch misses and 68M on D-port stalls to DDR.
