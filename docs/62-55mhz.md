# Step 62 — The board at 55.56 MHz

Steps 59 to 61 left the board core at 51.9–59.1 MHz over 8 seeds, timed
against 50 MHz. The next clock above 50 that still gives 115200 baud
within 0.5 % is the IO PLL / 18 = 55.56 MHz, with UART divisor 30
(115,741 baud, +0.5 %). The first sweep at that target passed on 4 of 10
seeds. Four more path fixes, none of which changes a cycle count, bring it
to 9 of 10, and the best seed gives 7.4 % margin.

## The result

| | Step 59 | Step 62 |
|---|---|---|
| core clock (FCLK1) | 50 MHz (IO PLL / 20) | **55.56 MHz** (IO PLL / 18) |
| after routing, shipped seed | 58.36 MHz (seed 6), 16.7 % margin | **59.69 MHz** (seed 7), **7.4 %** margin |
| seeds passing their target | 9 of 9 (55.3–58.4) | 9 of 10 (52.2–59.7) |
| CoreMark, iterations/s (CoreMark/MHz × MHz) | 92.7 (1.854) | **140.3** (2.526) |
| Dhrystone DMIPS (DMIPS/MHz × MHz) | 37.4 (0.747) | **65.2** (1.173) |
| U-Boot + Linux, reset to shell | 304.4M cycles, 6.1 s | 299.9M cycles, **5.4 s** |
| nextpnr LUT sites, flip-flops | 31 %, 13 % | 32 %, 14 % |
| block RAM | 16 RAMB36 + 2 RAMB18 | 17 RAMB36 + 2 RAMB18 |

The Linux boot takes more cycles at 55.56 MHz than Step 61's 284.5M at 50.
The console runs at a fixed baud, so every character costs 11 % more
cycles, and part of the boot waits on the console.

The bitstream is OpenZynq's `projects/riscv_linux/prebuilt/riscv_linux.bit`,
sha256 `c0d6610a…3211e91`, built with `--freq 55.56 --seed 7` (`OZ_FREQ`,
`OZ_SEED` in `tools/rvlinux`). The U-Boot + Linux image is unchanged:
U-Boot and Linux read the clock from the device tree the ROM writes.

## What carries the clock

- **The ROM and its device tree:** `BBL_DEFS` in the `Makefile`,
  `PLAT_CLOCK_HZ=55555556` and `UART_DIVISOR=30`. The DT's
  `timebase-frequency` and the UART's `clock-frequency` come from them.
- **The PS program:** FCLK1's divisors, 3 × 6 (`sw/linux/board/ps/main.c`).
- **`fpga_top_linux`:** the UART's reset divisor, `UART_DIV=30`.
- **The simulations:** `tools/rvboot`'s board-ddr divisor, the top-level
  bench's clocks per bit, and the HP0 model's FCLK1 period (18 ns).
- **nextpnr:** `--freq 55.56`, so placement is timing-driven against the
  real clock.

## The paths, build by build

Each row takes out what the previous sweep reported (10 seeds at
`--freq 55.56`).

| change | 10 seeds | pass |
|---|---|---|
| Steps 60–61, and SYSTEM-instruction commits without `ex_hold` | 52.6–58.5 | 4 |
| + an SC's reservation match registered; the ROM decoded as "below 1 MiB" | 51.4–57.0 | 2 |
| + the D-cache's word select from a register; the walker's level-1 PTE taken every cycle | **52.2–59.7** | **9** |

- **System commits.** A CSR access, `mret`, `sret` and `sfence.vma` never
  hold EX: no walk, divide, multiply or second lookup cycle is theirs.
  So with `XLATE_2C` their commits wait for `freeze` only. Without that,
  they also waited for `ex_hold` and the page walker's state behind it,
  on its way to every trap-CSR and counter write enable. A
  simulation-only check stops any run in which one does hold EX.
- **SC.** `freeze` depended on `sc_ok`, which was a 32-bit compare of
  the reservation address against MEM's. The compare is now made as the
  SC enters MEM, against the reservation it will meet there: an LR
  finishing in MEM at that edge sets it to that LR's address. With
  `XLATE_2C` an SC spends two cycles in EX, so that case cannot actually
  happen. A simulation-only check compares every SC against the old
  compare.
- **The ROM decode.** `dready` used the ROM's exact range, a pair of
  magnitude compares. The core's region check lets no access outside a
  real region reach the port, so on the block-RAM SoC "below 1 MiB" is
  the same answer for everything that arrives.
- **The word select.** The D-cache picks a word out of a 256-bit line that
  comes from 4 block RAMs. The select came from the D-port's address,
  behind the walker-or-MEM mux. `dcache_b` now registers the word it read
  for, next to the index and tag (`rword_q`). Its simulation-only check,
  "a read taken as the request's is for its address", now covers the
  word too.
- **The walker.** `ptw` loaded the level-1 PTE's pointer only when the PTE
  was neither bad nor a leaf, so the enable waited on decoding the data
  just read. It is only used in `S_L0`, and `S_L1` leaves for `S_L0` only
  at the read that brought it, so it now loads in every `S_L1` cycle.

The shipped seed's worst path is the core's own EX loop, forwarding →
ALU → `ex_result`, 16.8 ns.

## Where it stands

Not run on a board yet. 7.4 % is nextpnr's estimate. If the board
misbehaves at random, the Step 59 build is 50 MHz with 16.7 % margin, and
OpenZynq's prebuilt README says how to bring it back. The next
baud-exact clock is IO PLL / 16 = 62.5 MHz (divisor 34, −0.3 %), past
every seed here.
